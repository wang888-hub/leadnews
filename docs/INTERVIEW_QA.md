# 面试高频问答

每题先给可口述的 30 秒回答，再给追问展开。

## Redis

### 为什么用 Lua？
- **30 秒**：LIKE/UNLIKE 需要同时判断关系、改计数、写 pending，Lua 能让条件更新在 Redis 内原子完成。
- **深入**：普通 GET+SET 有并发窗口；脚本只有真实状态变化才产生事件，并防计数为负。

### 为什么不用分布式锁？
- **30 秒**：目标是单 Redis 内多 Key 原子状态迁移，Lua 比锁少一次往返，也没有锁续期/误删问题。
- **深入**：锁适合跨资源临界区，但这里仍无法解决 Redis 成功后 Kafka 失败，pending 才负责该窗口。

### LIKE/UNLIKE 如何幂等？
- **30 秒**：Lua 以用户-文章 relation 判断是否真正迁移，Consumer 再以 eventId 唯一键去重。
- **深入**：请求幂等与消息幂等是两层；重复 LIKE 不调整 counter，重复消息不更新 MySQL。

### Redis 挂了怎么办？
- **30 秒**：行为写返回 503，不伪造成功；Article 读降级 MySQL并标记非实时，Hot 返回降级数据。
- **深入**：恢复后 Article 自动预热；不同语义不能用一个统一 fallback。

### Redis 与 MySQL 不一致怎么办？
- **30 秒**：Redis 是实时层、MySQL 是持久真相；pending/Kafka 完成写收敛，绝对计数和离线任务可校准热点。
- **深入**：先查 pending、consumer lag、eventId 日志，再做可审计修复，不能直接 flush 或改数。

## Kafka

### 为什么用 Kafka？
- **30 秒**：项目需要行为削峰、发布事件、ES/摘要解耦和 Streams 热点，Kafka 可统一事件主线。
- **深入**：旧项目 RabbitMQ/Kafka 并存，本次减少组件，但仍必须显式设计分区、重试与幂等。

### 消息重复怎么办？
- **30 秒**：按至少一次接受重复，用 eventId 唯一键、终态 no-op 和版本 CAS消除副作用。
- **深入**：Producer 幂等不等于数据库端 exactly-once；DB commit 后 offset 未提交会重放，正是 Consumer 幂等场景。

### 消息丢失怎么办？
- **30 秒**：业务事务写 outbox/task；Redis 路径写 pending；只有本地持久证据存在后才异步投递。
- **深入**：失败记录有限重试，毒消息进 DLT；不能先提交业务再无记录地 send。

### Kafka 挂了怎么办？
- **30 秒**：行为 pending、搜索/摘要 outbox、审核任务保留；恢复后投递并检查 lag、状态和精确增量。
- **深入**：实测恢复后行为 pending=0，VIEW +1，稿件约 2.45 秒收敛。

### 为什么既要 pending 又要 outbox？
- **30 秒**：pending 解决 Redis 成功/Kafka 失败；outbox 解决 MySQL 事务成功/Kafka 失败，真相源不同。
- **深入**：二者目的相同但不能混用一种存储覆盖所有链路。

### eventId 如何设计？
- **30 秒**：生产时生成全局唯一 ID并贯穿重试，数据库唯一约束最终裁决。
- **深入**：重投不能生成新 ID，否则唯一键失效；极小碰撞也应作为冲突告警而非覆盖。

### 分区键如何选？
- **30 秒**：按需要顺序的业务实体，如 articleId/newsId，使同实体事件进入同分区。
- **深入**：全局顺序没有必要且会限制吞吐；仍需版本 CAS 防跨链路迟到。

## Kafka Streams

### 为什么热点不用普通 Consumer？
- **30 秒**：Streams 原生提供分组、5 秒窗口和状态恢复，适合把密集行为压成刷新信号。
- **深入**：它不是为了再次写计数；普通 Consumer 也能做，但窗口/状态管理需自行实现。

### 5 秒窗口是什么意思？
- **30 秒**：同一文章短时间内的多条行为合并为有限刷新次数，不是五秒后才持久化行为。
- **深入**：窗口降低热点重算频率，行为 MySQL 持久化由另一条 Consumer 链路完成。

### 为什么不能直接累加事件？
- **30 秒**：Lua 已经改过 counter，消息又累加会双计数；重放还会继续放大。
- **深入**：事件只表示“值变了”，热点读取权威实时绝对值重算。

### 为什么读取绝对 counter？
- **30 秒**：绝对值天然抵抗重复刷新，并让 Streams 与 XXL 离线重建使用同一输入和公式。
- **深入**：若 counter 丢失需从 MySQL校准，不能把 ZSet 自身当真相。

## MySQL 与一致性

### 为什么不用分布式事务？
- **30 秒**：MinIO、ES、Kafka、AI 无法经济地加入长事务，项目用本地事务、任务、幂等、版本和补偿。
- **深入**：代价是短暂不一致和更多状态，但恢复路径明确且故障隔离更好。

### 最终一致性如何实现？
- **30 秒**：先原子提交事实与待办，再至少一次投递，Consumer 幂等处理，失败重试/补偿并用状态可观察。
- **深入**：需要同时回答真相源、幂等键、重试上限、DLT/FAILED 和人工入口。

### CAS 用在哪里？
- **30 秒**：稿件审核、发布、摘要版本、任务领取和精确恢复都用“预期状态/版本”条件更新。
- **深入**：CAS 失败通常返回 no-op 或 409，阻止并发/陈旧操作，不代表数据库异常。

### 唯一约束用在哪里？
- **30 秒**：eventId 处理日志、稿件到正式文章、各版本任务等使用数据库唯一键作最终防线。
- **深入**：应用层先查只能优化体验，不能替代并发下的唯一约束。

### 为什么某些操作返回 409？
- **30 秒**：请求合法但资源状态不允许，例如编辑已发布稿件或重复推进状态。
- **深入**：409 与 403 不同：前者是状态冲突，后者是身份无权。

## Elasticsearch

### 为什么 ES 不做数据库？
- **30 秒**：ES 是可重建搜索投影，事务和业务状态以 MySQL 为准。
- **深入**：搜索优化的数据结构不应承担发布真相；删索引后应能重建。

### 索引和 MySQL 如何同步？
- **30 秒**：发布事务写 outbox，Kafka Consumer 幂等 upsert ES，失败保留 PENDING。
- **深入**：避免 MySQL 成功而同步 ES 调用失败造成无记录双写缺口。

### ES 挂了为何 Article 不受影响？
- **30 秒**：Article 读 MySQL/Redis，发布不等待 ES；只有 Search 能力明确 503。
- **深入**：实测恢复后约 22.6 秒 outbox 收敛并可检索。

### 如何重建索引？
- **30 秒**：从 MySQL 权威文章分页生成投影，在新索引完成后切 alias；增量 outbox 必须在重建窗口继续处理或回放。
- **深入**：当前实现具备事件投影基础，生产级 alias 双写/切换仍是后续项，不能声称已完整演练。

### 为什么 standard analyzer？
- **30 秒**：当前实际环境没有 IK，选择 ES 内置、版本兼容且可复现的 standard analyzer。
- **深入**：中文效果是权衡；联想另用 edge-ngram，不能文档写 IK 而部署未安装。

## MinIO

### 为什么静态化？
- **30 秒**：Freemarker 预生成正文页面，把稳定内容读取从数据库拼装移到对象存储。
- **深入**：元数据/状态仍在 MySQL；静态页是派生产物，可按文章重建。

### 为什么 deterministic objectKey？
- **30 秒**：固定 `article/{id}/index.html` 使失败重试覆盖同一对象，天然控制重复发布。
- **深入**：随机 UUID 会制造孤儿对象并让数据库提交失败难补偿。

### MinIO 故障如何恢复？
- **30 秒**：文章停在 PUBLISH_FAILED，不误标发布；恢复后 XXL 精确重试。
- **深入**：实测恢复约 606 ms，最终 objectKey 固定且重复执行幂等。

### 为什么这里也不用分布式事务？
- **30 秒**：对象存储不参加 MySQL 事务；用状态机、确定性 Key 和补偿比伪两阶段提交可靠。
- **深入**：上传成功/DB 失败时重试覆盖同一对象，后续也可做孤儿巡检。

## Sentinel

### Gateway 与 Service 限流区别？
- **30 秒**：Gateway 保护整体入口和 API 组；Service 更了解资源方法/参数，可保护单 articleId。
- **深入**：两层互补，不能只靠边缘限制所有内部流量。

### 热点参数限流是什么？
- **30 秒**：以 `articleId` 等参数值分别计数，单个热点不挤占其他文章配额。
- **深入**：实测两个 articleId 在同窗拥有独立放行量。

### 429 为什么不能有副作用？
- **30 秒**：429 表示请求未被业务接受，必须在 Lua/Kafka/Provider 之前拦截，前端也不能乐观更新。
- **深入**：实测 Behavior 放行 8 次时增量严格为 8。

### 为什么 AI 单独限流？
- **30 秒**：Provider 慢且收费，需要比普通 API 更低 QPS，并配合服务内 Semaphore/timeout。
- **深入**：实测 AI 规则阻断时请求指标不增加，证明未进入 Provider。

## Spring AI / Qwen

### 为什么 Spring AI？
- **30 秒**：统一 Chat/streaming 抽象、可测试适配和配置管理，降低业务代码对 Provider SDK 的耦合。
- **深入**：仍通过 Alibaba Adapter处理 Qwen 特定结构和错误，抽象不等于能力完全一致。

### 为什么需要 Adapter？
- **30 秒**：Provider 的模型参数、多模态消息、流式响应和错误码有差异，适配层把它们映射为内部稳定契约。
- **深入**：业务层不应散落 Provider JSON，也不能在 Adapter 中记录敏感 Prompt/Key。

### AI 审核失败怎么办？
- **30 秒**：统一记录错误类别并转 MANUAL_REVIEW，文章不会自动通过。
- **深入**：400不重试；连接/429/5xx有限重试；耗尽进入人工并保留轨迹。

### 为什么 parse failure 不能 PASS？
- **30 秒**：无法解析等于没有可信决策，默认 PASS 会把格式/基础设施故障变成审核漏洞。
- **深入**：必须校验必填、枚举和 confidence 范围，Markdown fence也需安全解析。

### 为什么需要 Semaphore？
- **30 秒**：限制单 JVM 同时占用的外部 AI 流，防慢请求耗尽线程、连接与预算。
- **深入**：拒绝应快速明确；取消、完成和异常路径都必须释放 permit。

### 为什么 Summary 异步？
- **30 秒**：摘要是增强字段，不应让 Provider 延迟或失败回滚 PUBLISHED。
- **深入**：独立任务可重试/FAILED/精确恢复，发布只负责创建待办。

### summaryVersion 有什么用？
- **30 秒**：内容新版本产生新摘要版本，旧异步结果即使迟到也不能覆盖。
- **深入**：Consumer 回写时 CAS 当前版本，旧任务标记 STALE。

## SSE

### 为什么 SSE 而非 WebSocket？
- **30 秒**：续写是一次请求、服务端单向输出，不需要持久双向连接，SSE 更简单且兼容 HTTP。
- **深入**：项目用 POST fetch 流解析以携带请求体；错误与取消要自行定义。

### SSE cancel 如何实现？
- **30 秒**：前端 AbortController 关闭 fetch，Reactor 感知 cancel，终止上游并在 finally 释放 Semaphore。
- **深入**：真实验证取消后下一请求能完成，证明许可没有泄漏。

### 客户端断开如何释放资源？
- **30 秒**：流上使用取消传播和 `doFinally`，把 COMPLETE/ERROR/CANCEL 都纳入清理。
- **深入**：只在 done 回调释放会漏掉断网和 Abort。

### 为什么 Nginx `proxy_buffering off`？
- **30 秒**：否则 chunk 会被代理攒批，浏览器失去逐块体验；同时关闭 gzip/cache。
- **深入**：阶段 14 分别验证 Vite 与 Nginx 流式首块，而非只看最终正文。

### 为什么续写不自动保存？
- **30 秒**：模型文本不可信且用户可能取消，只有用户显式采用并保存才能改稿件。
- **深入**：真实 smoke 前后正文哈希一致；AI 503也不影响编辑。

## 微服务与故障恢复

### 为什么拆这些服务、如何通信？
- **30 秒**：按领域所有权和失败边界拆 Gateway+8服务；同步用服务名 OpenFeign，异步用 Kafka。
- **深入**：服务不直接 Maven 依赖；Nacos做发现/配置，不把实例 IP 写死。

### internal API、用户头与 TraceId 如何处理？
- **30 秒**：Gateway拒绝外部 internal，删除伪造用户头并由 JWT 重建；TraceId 经 Gateway、MDC、Feign 透传。
- **深入**：internal header 仅本地边界，生产仍需 mTLS/服务身份。

### 五类依赖故障分别怎样？
- **30 秒**：Redis 写503/读降级；Kafka 留 pending/task；ES仅 Search503；AI审核转人工、摘要FAILED、续写error；MinIO进入PUBLISH_FAILED。
- **深入**：恢复分别靠预热、重投、outbox、精确AI重试、确定性对象键+XXL补偿，并核对最终数据而非只看 health。

## 性能口径

### 为什么没有测出“高 QPS”？
- **30 秒**：Sentinel 本地阈值先成为上限，饱和请求大多快速429，不能代表业务吞吐。
- **深入**：正常区间 Article 3.40 RPS/P95 45.21 ms，Search 2.88 RPS/P95 48.35 ms。

### 429 与真实服务失败区别？
- **30 秒**：429是预期容量保护且无副作用；5xx表示依赖/程序未完成请求，需要降级或修复。
- **深入**：压测必须分开统计，不能把快速429延迟混进成功P95。

### 为什么不宣称百万并发？本机测试有什么局限？
- **30 秒**：测试只有单机、localhost、60秒窗口和单节点基础设施，没有网络、集群、长时soak或冗余。
- **深入**：它能证明契约、限流和局部恢复，不能证明生产 SLA、容量或高可用。
